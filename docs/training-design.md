# 培训模式设计

> 状态：设计稿。**已实现**：guard 培训模式、领任务 / 发基线 / 验收单，以及一个与本稿出题方式不同的
> **改动小测**（见 §5a）。**尚未实现**：§4 的 G2 闸门与水印、§5 的三个题源。
> 目标读者：负责新生培训的老队员。

---

## 0. 前提：队里已经有一套培训体系

设计之前先把飞书里那份《软件知识体系、百事通》读完了。队里现有的东西比想象中完整：

- **分三层的培训流程** —— 实操技能（焊接 / Keil / CubeMX / VOFA、电调、DT35）、理论能力（单片机组成原理 / 外设 / FreeRTOS / 移动机器人学）、赛事相关（工程常识）
- **明确的验收机制** —— 原文：「需要每个学员在听完录播课后，对课上的实验进行复现，并由**老队员验收+提问**」
- **成文的代码规范** —— 《RCSLIB 代码规范》按 **要求 / 推荐** 两级写，本身就是一份规则清单
- **成文的教学法** —— 代码规范开篇写着「讲解和学习方式：**是什么 → 为什么 → 怎么做**」
- **第一个实操作业已经定好** —— `bit_actions.c/.h`，五个位运算函数，纯 C、无硬件依赖

还有一句话，直接决定了本设计的方向：

> 就算什么都不学，直接上手代码，照样能把机器人动起来，但这就失去了机器人比赛的意义。

**一个会写代码的 Agent，是「什么都不学就让机器人动起来」的最快路径。** 所以本设计的目标不是「让新生能用插件生成代码」——那太容易做到，也没有价值。目标是：

> **让 Agent 放大「老队员验收 + 提问」这个已经存在的机制，而不是替代它。**

---

## 1. 一个必须先说清楚的诚实前提

**锁是拦不住的。** 新生完全可以另开一个 DeepSeek 网页版，把题目粘进去要代码。任何「不做完测验就不给代码」的设计，都建立在一个不成立的假设上。

所以闸门的目的不是**阻止**，而是两件事：

1. **让好路径成为省力路径** —— 在插件里走「骨架 + 测试」比自己去外面复制粘贴更快、更容易通过验收
2. **让绕过留下痕迹** —— 生成的代码带水印，验收时如实呈现

把这一条写在最前面，是因为后面所有机制的强度都受它约束。设计不该假装自己能做到做不到的事。

---

## 2. 核心机制：训练模式作为另一种 guard 模式

`GuardMode` 增加 `'training'`，与 `'dev'` 并列。这天然契合已有架构 —— guard 是横切层，本来就拦截每一次 rcs 工具调用。

> **实现与本节初稿有两处出入，以代码为准（`packages/rcs-core/src/danger.ts`）：**
>
> 1. **L2 是「人工确认」，不是「一律拒绝」。** 初稿写的拒绝没有落地，因为培训
>    本身就要烧代码、要用 F407 —— 拦死等于整套培训跑不起来。确认这一步保留，
>    而且文案比 dev 更重：多一句「第一次做请让老队员在旁边，当面指认急停按钮」。
> 2. **参照物 `field`（赛场模式）已删除**，所以「等同赛场」这个说法不再有对象。
>
> 另外要如实说明：guard **按工具名精确匹配，只覆盖 `rcs_*`**。宿主自带的
> `bash` / `pwsh` / `write` 不经过它，学员完全可以绕开。这一层是提醒，不是沙箱 ——
> 与本文第 1 节「设计不该假装自己能做到做不到的事」是同一条原则。

训练模式下：

| 危险度 | 行为 |
|---|---|
| L0 只读 | 放行 |
| L1 本机写（构建、跑测试） | **放行** —— 这是学习循环的核心，必须顺畅 |
| L2 物理动作（烧录、电机使能、气路） | **人工确认**，文案含急停/使能线/限位要点 |
| **LG 代码生成**（新增一类） | 按下面的三档管控 |

L2 之所以只到确认而不拒绝：新生正是最容易低估红色急停、驱动使能线、限位保护的
那批人，每次弹一下把安全要点重复成肌肉记忆，比一刀切更贴合培训场景。

## 3. 三档产出，而不是一个「生成」开关

| 档 | 产出 | 何时可用 |
|---|---|---|
| **G0 讲解** | 只讲原理，指向队内文档 / 规则条款 / 模板代码的具体位置，**不出任何代码** | 永远 |
| **G1 骨架 + 会失败的测试** | 挖空的 `.c/.h` + 一份**当前必然失败**的 gtest | 默认档 |
| **G2 完整实现** | 完整可编译代码 | 需过闸门，且带水印 |

### G1 是主力，理由是队里已有的基础设施

`rcs_support_test` 已经能在 PC 上跑 gtest，**不需要任何硬件**。于是学习循环变成：

```
拿到骨架和红色的测试 → 填空 → 跑 rcs_support_test → 红变绿
```

这个循环本身就是最好的老师。而且它把**验收的机械部分自动化了**：老队员不必再逐份看「作业跑没跑通」，只看思路和提问。

`bit_actions` 那个作业是 G1 的完美样例 —— 五个函数、纯位运算、无外设依赖，测试用例可以**穷举**（`uint8_t` 的第 n 位一共就 8×256 种情况，全测得起）。测试穷举意味着「绿了就是真对了」，这在嵌入式培训里很难得。

### G0 不是安慰奖

代码规范里那句「是什么 → 为什么 → 怎么做」应当成为 G0 输出的固定结构。而且 G0 有一个 Agent 独有的优势：它能**指着队内的真实代码**讲，而不是讲教科书上的通用例子 —— `rcs_kb_search` 查得到飞书资料，`rcs_lint_*` 知道队里的分层红线，模板工程就在本地。

## 4. 闸门：G1 → G2

三个条件，各自可在 `config/training/` 里开关，默认全开：

**① 先交一次。** G1 骨架至少提交过一次能编译的尝试。不要求测试通过 —— 卡在「写不出来」的人正是最需要看答案的人，罚他们没有意义。要求「能编译」是因为连编译都没试过，说明根本没动手。

**② 答三问。** 针对该任务的三道题，来源见下一节。

**③ 留水印。** G2 产出的文件头带一段生成记录：

```c
/* [dsh4rcs:training] task=bit-actions gen=G2 at=2026-09-02T10:00Z
 * 本文件由 Agent 生成。验收时请核对作者是否理解每一行。
 * 生成前答题记录：3/3。 */
```

**第 ③ 条最重要，也最容易被低估。** 它让 `rcs_train_review` 在验收时能如实说「这段是 G2 生成的」。没有它，前两条闸门的意义会大打折扣 —— 老队员看到的只是一份来历不明的作业。

## 5. 题从哪来 —— 全设计最关键的一节

**手写题库必然腐烂。** 规范改了、模板代码变了，题还停在两年前，比没有更糟。

三个来源，**全部来自队内已有资料，没有一道是编的**：

### a. 代码规范的 要求/推荐 条目

《RCSLIB 代码规范》本身就是规则清单，而且天然带「是什么 / 为什么 / 怎么做」三段结构。每条 **要求** 可以直接成题：

> 「不应对浮点数做 `==` 判断」—— 为什么？下面哪种写法是对的？

### b. 变异题 —— 最有价值的一类

拿队内**真实文件**，注入一个 `rcs_lint_embedded` / `rcs_lint_layer` 能检出的缺陷，问「这段代码有什么问题」。

答案由 **linter 判定**，不需要人工维护答案键。这意味着：

- **自动生成**，题量不受人力限制
- **永远与规范同步** —— 规则改了，题跟着改
- **直接对应队内标准**，不是通用 C 语言题

这是把 `rcs_lint_*` 从「检查工具」变成「教具」，投入产出比最高的一项。

### c. 真实缺陷

已经在队内代码里查出的三个真实缺陷是最好的教材，尤其其中两个属于**沉默失败** —— 编译通过、运行不报错，只在赛场上表现为「今天车有点怪」。这类缺陷讲一百遍原理不如看一次真实案例。

### 一条必须守死的红线

**不许让模型编题。** LLM 生成的嵌入式 C 题目会产出「看起来合理、其实是错的」标准答案 —— 把错误知识以「标准答案」的权威形式教给新生，比不考试糟糕得多。所有题目必须可追溯到某条规范、某条 lint 规则，或某个真实缺陷。

## 5a. 已实现：改动小测（与 §4、§5 的出题方式不同）

§4 的「答三问」与 §5 的三个题源都是**考试**式的：题有标准答案，答对才放行。先落地的是另一件事 ——
**新生用 Agent 改了代码之后，就这次改动问几个开放题，回答留给老队员看**：

- **题目钉在改动上。** Agent 只能挑这次改动过的某一行，题型只有 why / what-if / edge 三种开放题，
  题干由模板生成。没有选择题、没有答案键 —— 模型挑位置，但不写标准答案，这样才守得住上面那条红线。
- **只记录，不判分，不拦路。** 回答原样存在学员本机的 `rcs-training/.records/`，不回传对话；学员可以不答，
  验收单会列出「还没答题的改动」。培训结束后 `npm run train:export` 导出，老队员 `npm run train:collect` 汇总。
- **不瞒学员。** 记录在学员自己的电脑上，瞒不住；问答框、领任务时都明说回答会给老队员看。
- **跟着 guard 的模式开关**，只在 `npm run dsh:start:training` 下开启。
- **可以追问，但提示不给答案。** 问答框最后有一栏可选的追问（每轮最多 2 次）：看不懂哪道题就先空着、写下想问的。
  追问原文交给模型，模型只能经 `rcs_train_hint` 回一段提示，工具把提示连同空着的题再弹一次，答过的题不再问。
  **这一条机器保证不了** —— 提示是模型写的。工具只拦得住太长（超过 200 字）、贴代码块、整行像代码的回复；
  提示原文存进记录，看过提示才答的题在报告里标出来，漏没漏答案由老队员核对。

它和 §1 是同一个前提：拦不住。学员可以让 Agent 替他答，Agent 也可以用 bash 写代码
（插件只看得到 dsh 的 write / edit / str_replace_editor）。所以记录的用处是给老队员挑追问的方向 ——
与 §8「提问那一半机器做不了」一致。实现见 `packages/rcs-core/src/training-quiz.ts`。

## 6. 课程数据化

`config/training/curriculum.json`，内容从飞书那份知识体系提炼：

```jsonc
{
  "id": "bit-actions",
  "title": "位操作封装",
  "stage": "keil-basics",          // 对应知识体系里的「基本常识培训+keil软件使用」
  "requires": [],                   // 前置任务
  "refs": [                         // 队内资料，由 rcs_kb_search 解析
    "软件知识体系、百事通#实操课任务",
    "RCSLIB代码规范#编码细节"
  ],
  "scaffold": "training/bit_actions/",
  "accept": {
    "tests": ["BitActions.*"],      // 这些 gtest 必须绿
    "lint": ["embedded", "layer"]   // 这些检查必须干净
  }
}
```

老队员加任务只改 JSON，不动代码 —— 与 `config/team.json` 的单一真相原则一致。

## 8. 老队员那一侧

`rcs_train_review` 输出的是**给人看的验收单**，不是自动判定「通过」。

因为知识体系里写的是「老队员验收**+提问**」——**提问那一半机器做不了**，也不该假装能做。工具负责把机械部分自动化（测试过没过、规范符不符合、有没有用 G2、答题记录如何），把老队员的时间省下来留给提问。

验收单大致长这样：

```
任务：bit-actions            提交人：（新生）
测试：8/8 通过
规范：干净
生成档位：G1（自己填的空）
答题：3/3

建议追问：
  - uint16_t 拆成两个 uint8_t 时，为什么必须显式转型？不转会怎样？
  - 小端合并那个函数，如果换到大端平台会发生什么？
```

追问的题目同样来自规范与 lint 规则，不是现编的。

## 9. 明确不做的事

- **不自动判定「学会了」** —— 测试绿了只说明代码对了，不说明人懂了
- **不给分数、不排名** —— 培训不是筛选
- **不让 G2 代码直接进正式工程** —— 水印 + 验收拦住
- **不编题**（见 §5 红线）
- **不碰焊接、硬件那部分培训** —— 那些本来就不该用 AI，知识体系里写得很清楚，要每人焊一条线再剪开焊回去

## 10. 一个已知的落地障碍

`runSupportTests` 有个不显眼的硬要求：队内仓库里那几个 `libgtest.a` 是**在 WSL/Ubuntu 下编译的 ELF 归档**，Windows 原生工具链链不了。

对老队员这不是问题（都装了 WSL），但**要求每个新生装 WSL 会劝退相当一部分人**，而 G1 循环的全部价值都建立在「跑测试」这一步顺畅上。

三个选项，需要队里定：

| 方案 | 代价 |
|---|---|
| 训练工程自带 CMake，用 FetchContent 现拉 gtest 源码本地编译 | 首次要联网、要装 MSVC 或 MinGW |
| 提供预编译的 Windows 版 `gtest.lib` | 要有人维护，换编译器版本要重编 |
| 要求装 WSL | 门槛最高，但和老队员环境一致 |

倾向第一个：训练任务是**独立的小工程**，不需要和队内 `RCS_Support/test` 共用那套库，可以自带一份干净的 CMake。

## 12. 分期建议

| 期 | 内容 | 依赖 |
|---|---|---|
| 一期 | training guard 模式 + `rcs_train_task` / `rcs_train_scaffold` / `rcs_train_review`，只做 `bit_actions` 一个任务打通闭环 | 只需 §10 定了 gtest 方案 |
| 二期 | 变异题引擎 + G2 闸门与水印（`rcs_train_quiz` 这个名字已由改动小测使用，见 §5a） | 需要一期跑过一轮 |
| 三期 | 课程表铺开、进度追踪 | 需要正式课程表 |

**一期只做一个任务是刻意的。** 培训体系最容易犯的错是一次铺开二十个任务，然后发现循环本身不顺 —— 先用 `bit_actions` 把「拿骨架 → 填空 → 跑测试 → 验收」跑通一轮真实新生，再谈铺开。
