## 一、权限模型：三层，一层比一层容易被忽略

| | 层 | 管什么 | 粒度 | 状态 |
|---|---|---|---|---|
| 一 | **scope（应用权限）** | 能不能调这类接口 | 应用级，无法按目录细分 | ✅ 已完成 |
| 二 | **协作者（资源授权）** | 能看到哪些目录 | 可精确到单个目录 | ✅ 已可读（但见第三层） |
| 三 | **实际范围** | **到底看到了多少** | —— | 🔴 **超出预期** |

前两层是「怎么开通」，第三层是「开通之后实际敞开了多大口子」。
**前两层绿了不代表第三层没问题**——本次就是如此。

| scope | 用途 | 状态 |
|---|---|---|

| `sheets:spreadsheet:readonly` | 读器件清单/测试记录表格 | ✅ |

| `docs:doc:readonly` | 读旧版文档正文 | ⚪ 未验证（授权范围内没有旧版文档） |
| `bitable:app:readonly` | 结论写回多维表格 | ⚪ 未验证（用不上，功能未实现） |

**必需权限已全部到位，且全是只读。** 目录遍历、44 篇文档正文都已实测通过。

> ⚠️ **申请权限时，页面上会同时出现同名的读写版**（`docx:document`、`drive:drive`、
> `sheets:spreadsheet` 等），**一律不要勾**。飞书的报错写的是「以下权限**任选其一**即可」，
> 读写版只是备选之一，不是"也要开"。本套工具全程只读，写权限没有任何用处，
> 只会放大出事的面。诊断脚本给出的链接**已经指向只读版**，照着点即可。

### ⚠️ 一个曾经误导过我们的坑

早先的诊断脚本拿 `doxcnProbeOnly` 这种**假 token** 去试接口，靠"是不是返回
99991672"判断权限。这是错的：**飞书先校验 token 格式、再校验权限**，
假 token 在权限检查之前就被格式校验挡回来，返回一个别的错误码，
于是被误判成"权限已通"。`docx` 因此被报了整整两轮**假绿**。

诊断脚本已改成从授权目录里**发现真实文档 token** 再探测；
范围内没有某个类型时如实报「未验证」，而不是打一个没验过的勾。

> 教训值得记：**假绿比红更危险**。红色会催人去处理，假绿让人以为已经做完了。

## 三、第二层：协作者——**这一步不用做了**

原计划是「把应用加为 A02 电控组(通用) / (硬件) 两个目录的协作者」。
实测发现**这一步是多余的**：

> `drive:drive:readonly` 一开通，应用**立刻就能读到整个根目录**，
> 没有任何人为它授权。共享文件夹对组织内身份（含应用身份）默认可读。

也就是说「加协作者来收窄范围」在这个结构下**根本不成立**——
加了是恒等操作，不加也照样能读。所以：

- ❌ 不用去点「添加文档应用」
- ❌ 也不用建群加机器人（顺带一提：本应用**未启用机器人能力**，那条路走不通）
- ✅ 直接进入第五节，范围收敛改在别处做

四个目录的 token 都已探明并写进 `config/team.json`，完整清单见第八节。
既然目录能直接列举，token **不需要人工从地址栏抄**——由脚本发现即可。

## 五、范围收敛现在落在哪里

既然飞书侧收不住，收敛只能落到**我们自己这一层**。`config/team.json`：

```json
"sources": [
  { "kind": "drive-folder", "label": "A02 电控组(通用)", "token": "El6Jfk…" },
  { "kind": "drive-folder", "label": "A02 电控组(硬件)", "token": "LF1kfh…" },
  { "kind": "drive-folder", "label": "A02 软件组",       "token": "fldcnz…" },
  { "kind": "drive-folder", "label": "A02 硬件组",       "token": "KHyVfT…" }
],
"sync": {
  "allowlistOnly": true,
  "includeTypes": ["docx", "doc", "sheet"],
  "excludeTypes": ["file", "shortcut", "bitable", "mindnote", "slides"],
  "maxDepth": 12
}
```

同步器**只从 sources 的 token 起步向下遍历**，并拒绝任何不在白名单子树内的 token；
`excludeTypes` 把安装包、压缩包这类二进制挡掉（实测跳过 **2423** 个）。

> `maxDepth` 从 6 调到 12 是实测决定的：深度 6 时有 21 个目录展不开。
> 调到 12 后覆盖全树（0 个未展开），而文档数仍是 44 —— 说明更深的层只有二进制。
> 这个数字该由实测定，不该凭感觉拍。

**要诚实地说清楚这道屏障有多强：**

| 它能防 | 它防不住 |
|---|---|
| 同步器写错、遍历到不该去的目录 | 有人拿着 `app_secret` 直接调飞书 API |
| 敏感内容进入本地镜像 → 进入模型上下文 | 应用凭证泄露后的越权读取 |

所以它是**纵深防御的一层，不是替代品**。第四节那两件事该做还是要做。
`app_secret` 之前贴进过聊天记录，**建议一并重置**——重置后只需重设一个环境变量。

## 七、常见卡点

| 症状 | 原因 | 怎么办 |
|---|---|---|
| 能列目录但读不到正文 | 只开了 `drive` 没开 `docx` | 两个都已开并实测通过 |
| 老文档读不出来 | 旧版文档走 `docs:doc:readonly` | **未验证** —— 当前授权范围内一篇旧版文档都没有，无法确认。真遇到时看 `feishu:check` 第一层 |
| 表格读不出来 | `sheets:spreadsheet:readonly` | 同上，范围内没有表格可供探测 |
| 想加群机器人但加不了 | 本应用未启用机器人能力 | 开放平台「应用能力」里加，但本路线用不上 |
| 同步很慢 / 报频控 | 飞书 API 有 QPS 限制 | 正常，同步做增量（只拉变更节点） |
| 换了 secret 后失效 | 环境变量没更新 | 重设 `FEISHU_APP_SECRET` 并**重开终端** |
